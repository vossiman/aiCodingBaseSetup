# T3 Code in a container

Each devpod workspace can run its own T3 Code server for steering agents from
the phone. Nothing runs until you set it up. State (identity, login, history)
lives on the host in `~/devpod/t3-envs/<workspace>`, mounted at
`~/.t3-envs`, so a rebuild keeps the pairing.

## Once per host

    mkdir -p ~/devpod/t3-envs        # on vossisrv, owned by your user

## Once per workspace

1. The project's `devcontainer.json` needs the `t3-envs` mount (new projects
   get it from the blueprint). A mount change needs one rebuild.
2. `t3-setup` logs in, links and enables agent activity. Sign in on the phone
   with the same account email the CLI reports.
3. `t3-start` (or `t3-start --dir PATH` to open sessions elsewhere).

## Commands

| Command | Does |
|---|---|
| `t3-start` | Start; it also starts at every container boot. |
| `t3-stop` | Stop; it no longer starts at boot. |
| `t3-status` | Server, versions, update mode, last result, `t3 connect status`. |
| `t3-update` | Switch to the newest t3 now (asks if work is running; `--yes` skips). |
| `t3-update X` | Switch to version X and hold it. |
| `t3-update --latest` | Follow new releases again. |
| `t3-auto off` / `on` | Stop or allow automatic restarts for this workspace. |
| `t3-adopt --version X` | Take over existing t3 state without changing it. |
| `t3-migrate` | Move a container-local `~/.t3` onto the mount (below). |

## How updates happen

Every updater pass (about every 6 hours) looks up the newest t3 on npm and
installs it next to the running one. It restarts the server only when the
workspace follows `latest`, `t3-auto` is on, and t3 has been quiet for an
hour: no running turn, no waiting approval, no activity in any thread, no
busy process, no terminal typed in, and no CPU use across a one-minute
window. Anything it cannot check counts as busy. If the server crashed and
`t3-auto` is on, the updater still installs the new version and the next
start switches to it. After `t3-stop` the updater leaves the workspace
alone; run `t3-update` to switch.

Every switch backs up the database and identity first (last three kept) and
rolls back automatically if the new version does not come up.

Blind spot: an agent that scheduled its own wake-up more than an hour away
looks idle. Use `t3-auto off` while such a run is active.

## Moving an existing ~/.t3 (no re-pairing)

1. In the old container: make sure these commands exist (`aicoding-sync`),
   then `t3-migrate --export`.
2. Add the mount to the project's `devcontainer.json`, merge, rebuild.
3. In the new container: `t3-migrate --restore`, check `t3-status` and the
   phone (same computer, no new pairing), then `t3-migrate --confirm`.

## Recovery

If `t3-status` shows ATTENTION, an interrupted switch could not be finished
automatically. Every command except `t3-status` refuses until it is resolved:

1. Read `~/.t3-envs/<workspace>/aicoding/switch.json` (the old and intended
   versions and the backup folder).
2. Make sure `~/.t3-envs/<workspace>/userdata/` holds a complete copy (the
   backup folder has the database, `environment-id` and `secrets/`). A
   half-finished restore may have left `userdata.restore-<id>/` or
   `userdata.old-<id>/` beside it; take what you need, then delete them and
   `userdata.restore-<id>.complete`.
3. Delete `aicoding/switch.json` and `aicoding/attention`, then `t3-start`.
